
# C170.1 — Repository Intelligence Core

Status: Implementation candidate
Scope: Read-only repository inspection
Runtime: Node.js + repository-installed TypeScript
Dependencies added: None
Schema version: 1

## 1. Purpose

C170.1 establishes a deterministic, read-only repository context layer for
AIOS engineering workflows.

Its purpose is to reduce incorrect code generation caused by incomplete,
stale, or unverified repository context.

The module provides:

1. Git HEAD and branch identification.
2. Tracked-file inventory.
3. Git blob SHA and local SHA-256 for tracked files.
4. TypeScript project loading through the repository tsconfig.json.
5. Static module dependency resolution.
6. Reverse-importer discovery.
7. Likely test-file discovery.
8. Bounded target-file context generation.
9. Fail-closed behavior when repository state or context is incomplete.

C170.1 is an independent read-only foundation. It does not modify repository
files, create commits, call GitHub APIs, or invoke deployment services.

## 2. Design Principles

### 2.1 Repository truth first

Engineering context must be derived from the actual Git repository and its
checked-out files.

The module records:

- Current Git HEAD.
- Current branch, or detached HEAD state.
- Tracked repository files.
- Git blob SHA for each tracked file.
- SHA-256 calculated from each local tracked file.
- TypeScript source files and their resolved dependency relationships.

### 2.2 Fail closed

The module must stop when it cannot establish reliable repository context.

It must not silently truncate context, silently ignore unresolved internal
dependencies, or treat a stale repository index as current.

### 2.3 Read-only execution

The module does not:

- Write or modify source files.
- Create or modify Git commits.
- Create branches.
- Push to GitHub.
- Merge pull requests.
- Modify production data.
- Access GitHub, Vercel, or model-provider credentials.
- Execute generated code.

### 2.4 No new runtime dependency

The module uses Node.js built-in modules and the TypeScript package already
installed by the repository.

No additional package is introduced by C170.1.

## 4. Runtime Requirements

Run commands from the repository root.

Requirements:

- Node.js runtime compatible with the repository.
- Git installed and available on PATH.
- Repository dependencies installed.
- The repository TypeScript package available.
- A valid root tsconfig.json.
- A Git worktree with no tracked modifications.

The module does not install dependencies automatically.

## 5. Commands

### 5.1 Repository snapshot

Run:

```bash
node scripts/aios-engineering-context.mjs snapshot
```

The command emits a JSON repository index containing:

- schemaVersion
- repositoryRoot
- head
- branch
- generatedAt
- trackedFileCount
- trackedBytes
- trackedFiles
- typescriptSourceCount
- graph.dependencies
- graph.reverseDependencies

Each tracked-file entry contains:

- path
- bytes
- sha256
- blobSha

The dependency graph contains repository-relative paths for resolved,
tracked TypeScript dependencies.

### 5.2 Target inspection

Run:

```bash
node scripts/aios-engineering-context.mjs inspect lib/example.ts
```

Replace lib/example.ts with an actual tracked TypeScript file.

The command emits a JSON inspection result containing:

- schemaVersion
- repository.head
- repository.branch
- target
- directDependencies
- reverseImporters
- likelyTests
- rootConfigurations
- contextCharacters
- context

The generated context includes:

1. Target path.
2. Direct dependencies.
3. Reverse importers.
4. Likely test candidates.
5. Root configuration files.
6. Target source.
7. Direct dependency source.
8. Reverse importer source.
9. Candidate test source.
10. Available root configuration source.

The command emits the complete context or fails. It does not silently
truncate the context.

## 6. Dependency Graph

The implementation uses the repository TypeScript compiler API.

It recognizes these module reference forms:

- Import declarations.
- Export declarations with module specifiers.
- Import type references.
- Dynamic import with a string literal.
- require with a string literal.

The TypeScript compiler configuration is loaded from the repository's
tsconfig.json.

Internal dependencies are resolved using the configured TypeScript module
resolution options.

The graph includes tracked TypeScript source files inside the repository.

External dependencies outside the repository are not added to the
repository-local dependency graph.

Unresolved relative imports and unresolved @/ alias imports cause the
operation to fail.

### 6.1 Graph limitations

C170.1 does not claim complete semantic dependency analysis.

It does not currently guarantee discovery of:

- Computed dynamic import paths.
- Computed require paths.
- Runtime dependencies hidden behind reflection.
- Dependencies generated outside the TypeScript project.
- Non-TypeScript dependency relationships.
- All framework-specific implicit dependencies.

These limitations must be considered before using the generated context
as the sole basis for a high-impact code change.

## 7. Test Candidate Discovery

The inspection operation searches tracked files for likely test candidates.

Recognized test patterns include:

- *.test.ts
- *.test.tsx
- *.spec.ts
- *.spec.tsx
- Files inside __tests__ directories.
- Files under tests/ or test/.
- Matching candidates in the same directory.
- Files containing autonomous-development in their path.

Candidates are sorted and limited to a maximum of 40.

This is a heuristic discovery mechanism. It does not prove that every
relevant test has been found.

## 9. Resource Limits

The current implementation defines these fixed limits:

| Resource | Limit |
| --- | ---: |
| Tracked files | 20,000 |
| Individual tracked file size | 2 MiB |
| Total tracked worktree size | 100 MiB |
| TypeScript graph files | 12,000 |
| Test candidates | 40 |
| Generated target context | 200,000 characters |

When a limit is exceeded, the operation fails with an explicit error.

The implementation does not silently reduce the repository inventory or
truncate generated target context to fit these limits.

## 10. Independent Verification

The test file is:

scripts/aios-engineering-context.test.mjs

Run the tests directly:

```bash
node --test scripts/aios-engineering-context.test.mjs
```

The current test suite covers ten cases:

1. Snapshot records HEAD, tracked files, and content hashes.
2. Snapshot excludes untracked files.
3. Snapshot fails closed when the tracked worktree is dirty.
4. Inspection returns direct dependencies and reverse importers.
5. Inspection rejects path traversal.
6. Inspection rejects untracked target files.
7. Snapshot fails closed for unresolved internal dependencies.
8. Inspection rejects a dirty worktree even when an existing index is supplied.
9. Inspection rejects an index from an older HEAD.
10. Inspection fails closed when context exceeds the configured limit.

Tests use temporary Git repositories and clean up their fixtures.

The tests must run independently of production data and must not require
GitHub credentials, Vercel credentials, or model-provider API keys.

## 11. Required CI Validation

C170.1 must be validated on the same checked-out commit in GitHub Actions.

The required commands are:

### 11.1 Independent C170.1 tests

```bash
node --test scripts/aios-engineering-context.test.mjs
```

### 11.2 Repository TypeScript validation

```bash
npm run typecheck
```

### 11.3 Production build

```bash
npm run build
```

All three steps must execute successfully.

A green workflow result is not sufficient by itself if the workflow did
not execute these three commands.

The Actions run must provide evidence that:

- The workflow checked out the intended commit SHA.
- The C170.1 independent test command actually ran.
- The TypeScript typecheck actually ran.
- The production build actually ran.
- Each required step completed successfully.

A previous successful workflow that did not execute the C170.1 test command
does not establish that the C170.1 independent tests passed.

## 12. Security and Operational Boundaries

C170.1 is a read-only repository intelligence module.

It does not authorize an engineering agent to:

- Change the main branch.
- Create or merge pull requests.
- Bypass Founder approval.
- Push generated code.
- Change production configuration.
- Deploy to production.
- Modify secrets.
- Execute unreviewed generated code.

Repository inspection is not code-change authorization.

A valid repository context is necessary for safe engineering work, but it
does not replace independent verification or human approval.

## 13. Integration Boundary

C170.1 must remain independently testable before integration with the
existing autonomous development agent.

The next integration stages must preserve the following order:

Repository truth
    -> Context construction
    -> Dependency impact analysis
    -> Code generation
    -> Independent verification
    -> Delivery review
    -> Explicit Founder approval

C170.1 must not directly trigger code generation, file writes, commits,
pull requests, merges, or production deployments.

No existing autonomous development workflow should be changed merely
because this repository intelligence module exists.

## 14. Acceptance Criteria

C170.1 can be considered independently validated only when all of the
following are true:

1. The three C170.1 files exist on the intended commit.
2. The documentation accurately describes the implementation.
3. The independent test suite passes in GitHub Actions.
4. npm run typecheck passes in GitHub Actions.
5. npm run build passes in GitHub Actions.
6. The Actions logs confirm all three required commands actually ran.
7. All results correspond to the same commit SHA.
8. No production data or deployment state was modified by the tests.
9. No Founder approval boundary was bypassed.

Until these conditions are verified, the phase must not be represented
as fully validated.

## 15. Next Phase

The next planned phase is:

C170.2 — Dependency Impact Analyzer

C170.2 should use the repository context produced by C170.1 to identify
the likely impact of a proposed file change.

It should identify:

- Direct dependencies.
- Reverse importers.
- Related test candidates.
- Relevant configuration files.
- Potentially affected project areas.
- Missing or unresolved context.

C170.2 must preserve the read-only and fail-closed principles established
in C170.1.

C170.2 must not be integrated into production autonomous code modification
