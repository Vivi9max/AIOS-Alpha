C170.3 — Multi-provider Engineering Adapter

Status: Implementation candidate
Scope: Independent engineering model adapter with pre-dispatch secret scanning
Runtime: Node.js 24+
Dependencies added: None
Schema inputs: C170.1 schemaVersion 1 and C170.2 schemaVersion 1

1. Purpose

C170.3 provides an independent model-provider adapter for AIOS engineering workflows.

It separates engineering model calls from the existing product chat router.

The adapter accepts:

* Repository context produced by C170.1.
* Dependency impact reports produced by C170.2.
* A bounded engineering task description.

Before any external provider request, the complete outgoing engineering prompt must pass through the C170.3 Secret Guard.

The adapter returns a model-generated engineering proposal for Founder review.

It does not modify the repository or execute generated code.

3. Supported providers

The initial adapter supports OpenAI-compatible Chat Completions APIs:

Provider	API key environment variable	Default model
DeepSeek	DEEPSEEK_API_KEY	deepseek-chat
Qwen	QWEN_API_KEY	qwen-plus
OpenAI	OPENAI_API_KEY	gpt-4.1-mini

Provider endpoints and models can be overridden independently.

DeepSeek

* AIOS_ENGINEERING_DEEPSEEK_BASE_URL
* AIOS_ENGINEERING_DEEPSEEK_MODEL
* DEEPSEEK_BASE_URL
* DEEPSEEK_MODEL

Qwen

* AIOS_ENGINEERING_QWEN_BASE_URL
* AIOS_ENGINEERING_QWEN_MODEL
* QWEN_BASE_URL
* QWEN_MODEL

OpenAI

* AIOS_ENGINEERING_OPENAI_BASE_URL
* AIOS_ENGINEERING_OPENAI_MODEL
* OPENAI_BASE_URL
* OPENAI_MODEL

Provider order can be configured using:

AIOS_ENGINEERING_PROVIDER_CHAIN=deepseek,qwen,openai

The default order is:

deepseek,qwen,openai

Only providers with configured API credentials are attempted.

The adapter does not use Mock as a successful engineering provider.

4. Input contract

The exported function is:

runEngineeringTask(options)

Required fields:

* task
* repositoryContext
* impactReport

Optional fields:

* providerChain
* env
* fetchImpl
* timeoutMs
* maxOutputChars

C170.1 repository context

The context must contain:

* schemaVersion equal to 1
* repository.head
* repository.branch
* target
* directDependencies
* reverseImporters
* context

The repository HEAD must be a valid 40- or 64-character hexadecimal commit identifier.

The context must not exceed 200,000 characters.

C170.2 impact report

The impact report must contain:

* schemaVersion equal to 1
* analyzer equal to C170.2
* repository.head
* changedFiles
* affectedFiles
* perFile
* risk.level
* readOnly equal to true
* requiresFounderReview equal to true

The impact report HEAD must exactly match the C170.1 context HEAD.

The serialized impact report must not exceed 300,000 characters.

Mismatched or incomplete evidence is rejected before any provider request.

5. Provider behavior

The adapter:

1. Validates task and repository evidence.
2. Resolves the configured provider chain.
3. Builds the final engineering prompt.
4. Runs the mandatory Secret Guard against the complete outgoing prompt.
5. Rejects the request immediately if suspicious credentials are detected.
6. Skips providers without credentials.
7. Sends the bounded request to the first configured provider.
8. Validates the HTTP response.
9. Rejects empty or oversized model output.
10. Attempts the next configured provider after a provider failure.
11. Returns an explicit failure if all configured providers fail.

Secret scanning must occur before the first external provider request.

A secret scan failure must not trigger provider failover.

A provider failure must never be represented as successful model output.

The adapter does not silently fall back to Mock.

6. Security boundaries

6.1 Repository and execution boundaries

The adapter:

* Does not write repository files.
* Does not execute generated source code.
* Does not create branches.
* Does not commit changes.
* Does not push to GitHub.
* Does not create or merge pull requests.
* Does not deploy to Vercel.
* Does not modify production data.
* Does not read GitHub or Vercel credentials.
* Does not log API keys.
* Redacts provider API keys from returned provider errors.
* Uses a bounded request timeout.
* Uses bounded task, context, impact, and output sizes.
* Treats repository content as untrusted input.

6.2 Mandatory Secret Guard

All outgoing engineering prompts must pass through:

scripts/aios-engineering-secret-guard.mjs

The scan must cover the complete serialized payload containing:

* Engineering task description.
* C170.1 repository context.
* C170.2 dependency impact report.

The Secret Guard must execute immediately before external provider dispatch.

No external provider request may occur before the scan succeeds.

6.3 Fail-closed behavior

When suspicious credentials are detected:

* Reject the engineering request immediately.
* Use error code AIOS_ENGINEERING_SECRET_SCAN_BLOCKED.
* Do not dispatch the request to any provider.
* Do not attempt provider failover.
* Do not include the original credential value in error messages.
* Do not include the original credential value in finding metadata.
* Do not log the matched credential.
* Return only non-sensitive finding classifications.

The Secret Guard must not expose a configuration switch, environment variable, or normal runtime option that disables or bypasses mandatory scanning.

6.4 Heuristic detection limitations

The Secret Guard uses heuristic pattern detection.

It may detect common credential formats and suspicious sensitive assignments, including:

* GitHub token patterns.
* AWS access key patterns.
* OpenAI-style API key patterns.
* Google API key patterns.
* Slack token patterns.
* Bearer token patterns.
* JWT-shaped credentials.
* PEM private key headers.
* Quoted API key, token, password, and secret assignments.

These patterns are not an exhaustive credential classifier.

The scanner may produce false positives and false negatives. It cannot guarantee detection of every secret format, encoded credential, transformed value, custom token, or credential hidden in an unsupported representation.

A successful scan means only that the implemented heuristic rules did not detect a suspicious credential in the scanned payload.

It must never be described as proof that the payload contains no secrets or that external disclosure is absolutely safe.

Repository content may contain malicious or irrelevant instructions. The adapter explicitly instructs the model to treat supplied repository content as untrusted data.

This instruction is a mitigation, not a guarantee that model output is safe.

7. Result contract

Successful result:

* success: true
* status: PROPOSAL_READY
* provider
* model
* requestedProviders
* fallbackUsed
* attempts
* content
* repositoryHead
* impactRisk
* requiresFounderReview: true
* readOnly: true

No configured provider:

* success: false
* status: NO_CONFIGURED_PROVIDER
* provider: null
* content: null
* readOnly: true

All configured providers failed:

* success: false
* status: ALL_PROVIDERS_FAILED
* provider: null
* attempts
* content: null
* readOnly: true

Secret scan blocked:

* Request rejected before provider dispatch.
* Error code: AIOS_ENGINEERING_SECRET_SCAN_BLOCKED
* No provider request or failover.
* No original credential value in error metadata.

A successful model response is only a proposal.

It is not evidence that code has been changed, tested, committed, merged, or deployed.

8. Independent tests

Run the original adapter tests:

node –test scripts/aios-engineering-provider-adapter.test.mjs

Run the Secret Guard tests:

node –test scripts/aios-engineering-secret-guard.test.mjs

Run the provider security boundary tests:

node –test scripts/aios-engineering-provider-security.test.mjs

The original adapter test suite covers:

1. Matching C170.1 and C170.2 evidence.
2. Missing repository context.
3. Stale impact report HEAD.
4. Missing Founder review boundary.
5. No configured provider.
6. Provider failover.
7. Empty model output.
8. API key redaction.
9. Oversized repository context.
10. Oversized task.
11. Invalid provider chain.
12. Invalid timeout.
13. Request URL and payload.
14. Validation before network access.
15. Read-only result metadata.

The Secret Guard test suite must cover:

1. Ordinary engineering source code.
2. OpenAI-style credential detection.
3. GitHub token detection.
4. AWS access key detection.
5. PEM private key detection.
6. Bearer token detection.
7. JWT-shaped credential detection.
8. Sensitive assignment detection.
9. Password assignment detection.
10. Environment variable references and placeholder handling.
11. No credential values in finding metadata.
12. Fixed fail-closed error code.
13. No configurable bypass.

The provider security boundary test suite must cover:

1. Secrets in engineering task descriptions.
2. Secrets in C170.1 repository context.
3. Secrets in C170.2 impact reports.
4. No credential values in thrown errors.
5. Provider failover cannot bypass the Secret Guard.
6. Zero provider network calls after a scan failure.
7. Safe engineering tasks can reach the provider.
8. Founder review and read-only result boundaries remain intact.

All provider calls use an injected fake Fetch implementation.

The test suites do not require API keys, network access, or paid model calls.

10. Integration boundary

C170.3 is an isolated adapter.

It must not replace or modify:

* lib/ai/router.ts
* lib/ai/registry.ts
* lib/ai/types.ts
* lib/runtime/providerManager.ts

Integration with autonomous development is deferred.

The required future sequence is:

C170.1 Repository Context
-> C170.2 Dependency Impact
-> C170.3 Engineering Model Proposal
-> C170.4 Independent Verification
-> C170.5 Verified Delivery
-> C170.6 Founder Approval

No model-generated proposal may bypass independent verification or explicit Founder approval.
