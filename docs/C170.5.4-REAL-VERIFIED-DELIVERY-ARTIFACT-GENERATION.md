# C170.5.4 — Real Verified Delivery Artifact Generation

Version: C170.5.4
Status: Implementation Delivered — Awaiting GitHub Actions Verification
Runtime: Node.js 24+
Dependencies: Existing AIOS Alpha dependencies only

## 1. Objective

C170.5.4 upgrades C170.5 from tested artifact-generation capability to an
automated CI delivery pipeline.

The pipeline must:

1. Bind the delivery to an exact candidate Git Commit.
2. Generate a real C170.4 verification receipt.
3. Invoke the existing C170.5 delivery builder CLI.
4. Generate a complete delivery artifact outside the repository.
5. Independently verify the artifact against Git objects.
6. Recompute C170.2 dependency impact.
7. Revalidate the embedded C170.4 receipt.
8. Verify file content and SHA-256 values.
9. Preserve the generated artifact and verification report.
10. Keep Founder approval and production integration separate.

## 3. Real CI Generation Sequence

The candidate-branch workflow executes:

1. Checkout the complete Git history.
2. Install existing dependencies.
3. Run C170.1 through C170.5 tests.
4. Run the C170.5.4 independent verifier tests.
5. Run C169.8-D2.1 verification.
6. Run project continuity verification.
7. Run TypeScript typecheck.
8. Run the production build.
9. Execute the fixed C170.4 verification plan.
10. Save the C170.4 receipt under the runner temporary directory.
11. Resolve the merge-base between `origin/main` and candidate HEAD.
12. Execute the C170.5 builder CLI using the exact base SHA and receipt.
13. Generate the delivery JSON outside the repository.
14. Execute the independent C170.5.4 verifier.
15. Generate a SHA-256 manifest.
16. Upload the independently verified artifact and reports.

Artifact generation runs only on non-main branch push events.

It does not run on main pushes or pull-request merge refs.

## 4. Independent Verification

The verifier does not trust the builder's in-memory result.

It reads the generated JSON from disk and independently checks:

### 4.1 Commit binding

- Base SHA is a full commit SHA.
- Candidate SHA is a full commit SHA.
- Candidate SHA equals the checked-out Git HEAD.
- Base SHA is an ancestor of Candidate SHA.
- Artifact repository metadata matches both SHAs.

### 4.2 Git change manifest

The verifier recomputes:

`git diff --no-ext-diff --no-renames --name-status -z`

It requires the artifact file list and change statuses to match the actual Git diff.

Only added, modified, and type-changed files are accepted.

Deleted files, renamed files, copied files, and unsupported change types are rejected.

### 4.3 Git Tree and immutable blobs

Every delivered file must:

- Resolve to exactly one Git Tree entry.
- Be a regular Git blob.
- Use mode `100644` or `100755`.
- Match the exact candidate Git blob bytes.
- Match the recorded byte count.
- Match the recorded SHA-256.

The verifier does not trust the artifact's embedded file content or hash without comparing it to Git.

### 4.4 C170.2 impact report

The verifier invokes the real C170.2 analyzer again.

It independently compares:

- Analyzer identity.
- Changed-file list.
- Affected-file count.
- Affected-file details.
- Likely test candidates.
- Analyzer limitations.
- Risk classification.

A mismatch rejects the artifact.

### 4.5 C170.4 verification receipt

The verifier invokes the existing receipt verifier.

It requires:

- A valid receipt.
- A passing receipt.
- The exact candidate Commit SHA.
- Matching receipt checksum.
- Matching completed and expected check counts.
- An explicit unsigned-attestation status.

A receipt checksum is not a digital signature and does not authenticate the CI runner.

### 4.6 Founder approval boundary

The following values are mandatory:

- `founderApproval.required = true`
- `founderApproval.approved = false`
- `founderApproval.mergeAuthorized = false`
- `founderApproval.productionDeploymentAuthorized = false`
- `rollback.automaticRollback = false`

Any artifact that changes these values is rejected.

## 5. Artifact Output and Retention

The generated files are placed under the GitHub Actions runner temporary directory.

They are not committed to the source repository.

The workflow preserves:

- `aios-verified-delivery.json`
- `aios-delivery-builder-summary.json`
- `aios-delivery-verification.json`
- `aios-delivery-artifact.sha256`

Retention:

7 days.

The delivery JSON contains the changed file contents. Access to the workflow artifact should therefore be treated as access to the candidate source changes.

The C170.3 Secret Guard runs before artifact construction. It is heuristic and cannot guarantee detection of every possible secret.

## 6. Limits

The existing C170.5 limits remain:

| Limit | Value |
|---|---:|
| Changed files | 100 |
| Individual file | 5 MiB |
| Total delivered file content | 50 MiB |
| Independent verifier input | 256 MiB |

The verifier accepts only UTF-8 text files supported by the builder.

C170.2 remains static and heuristic.

C170.4 remains an unsigned process-observation receipt.

## 7. Security and Authority Boundaries

C170.5.4 does not:

- Create or modify a Git branch.
- Create a Git commit.
- Create or approve a pull request.
- Merge a candidate branch.
- Modify `main`.
- Deploy to Vercel.
- Change production data.
- Grant Founder approval.
- Authorize automatic rollback.

The uploaded artifact is evidence for Founder review, not merge authorization.

## 8. Acceptance Criteria

C170.5.4 is accepted only after an actual candidate-branch GitHub Actions run demonstrates:

1. Existing C170.1–C170.5 checks pass.
2. C170.5.4 verifier tests pass.
3. C170.4 receipt generation succeeds.
4. The real C170.5 CLI creates a non-empty artifact.
5. The independent verifier returns `status: VERIFIED`.
6. Git blob content and file SHA-256 checks pass.
7. C170.2 impact recomputation matches.
8. C170.4 receipt verification passes.
9. Founder approval remains false.
10. Merge and production deployment authorization remain false.
11. The SHA-256 manifest is created.
12. GitHub Actions successfully preserves the artifact.

A successful unit-test run alone does not satisfy C170.5.4.

A successful artifact upload alone does not satisfy C170.5.4.

A successful C170.5.4 run does not authorize merging or production deployment.

## 9. Founder Review

After CI acceptance, review:

- Candidate branch and commit SHA.

- Changed-file list.
