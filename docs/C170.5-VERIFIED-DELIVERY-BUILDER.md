C170.5 — Verified Delivery Builder

Version: C170.5.1
Status: Implementation Candidate — Pending Real Repository Integration
Runtime: Node.js 24+
Dependencies: No additional dependencies

1. Purpose

C170.5 introduces a verified delivery builder for AIOS Alpha.

Its purpose is to generate a complete, auditable delivery artifact from an immutable candidate Git commit.

The builder MUST read source file contents directly from the Git object database. It MUST NOT use working-tree file contents as the delivery source.

C170.5 binds together:

* An explicit base commit SHA.
* An immutable candidate commit SHA.
* The exact Git base-to-candidate changed-file set.
* A C170.2 dependency impact report for the same candidate commit.
* A fully passing C170.4 verification receipt for the same candidate commit.
* Complete supported file contents.
* Per-file SHA-256 digests.
* A complete artifact SHA-256 digest.
* Rollback guidance.
* An explicit Founder approval boundary.

The generated artifact is evidence of a candidate delivery. It is not authorization to merge or deploy.

3. Inputs and Contracts

3.1 Base Commit

The builder requires an explicit full 40-character Git commit SHA.

The base commit must resolve to an existing commit in the local repository.

3.2 Candidate Commit

The candidate commit must also resolve to an existing full 40-character Git commit SHA.

The candidate SHA identifies the exact source of every delivered file.

The builder must never substitute:

* Current working-tree contents.
* Uncommitted changes.
* A different branch HEAD.
* A mutable branch name.

3.3 C170.2 Impact Report

The builder requires a valid C170.2 impact report.

Required conditions:

* schemaVersion equals 1.
* analyzer equals C170.2.
* repository.head equals the candidate commit SHA.
* readOnly equals true.
* requiresFounderReview equals true.
* changedFiles is an array.
* risk.level is present.

The reported changed-file set MUST exactly match the Git base-to-candidate diff.

No missing or additional file is permitted.

C170.2 uses static dependency analysis and does not guarantee complete runtime impact detection.

Its output must be treated as an engineering risk assessment, not proof of complete dependency coverage.

3.4 C170.4 Verification Receipt

The builder MUST use the actual C170.4 verification implementation.

Expected interface:

verifyVerificationReceipt(receipt, expectedCommitSha)

The receipt must:

* Pass schema validation.
* Match the candidate commit SHA.
* Pass the fixed verification plan.
* Contain all required successful checks.
* Pass receipt checksum validation.
* Report an overall successful verification result.

A test substitute is not acceptable as evidence of production integration.

The receipt checksum is an integrity check, not a cryptographic signature or proof of runner identity.

4. Git Diff and File Integrity

The builder obtains the candidate change set using Git.

The comparison is:

baseCommitSha → candidateCommitSha

The supported change statuses are:

* A: Added.
* M: Modified.
* T: Type changed.

Unsupported changes must fail closed.

Currently unsupported:

* Deleted files.
* Renamed files.
* Copied files.
* Binary files.
* Invalid UTF-8 content.

These limitations exist because the current C170.2 analysis contract does not provide complete corresponding change modeling.

The builder MUST NOT silently omit unsupported changes.

Every supported file must be read using its candidate Git object.

Every file record contains:

* Repository-relative path.
* Git change status.
* Byte count.
* SHA-256.
* Complete UTF-8 file content.

The generated artifact also receives a SHA-256 digest calculated over its serialized JSON representation.

5. Resource Limits

The builder must enforce resource limits before completing delivery generation.

C170.2 currently has a maximum supported analysis scope of 100 changed files.

Therefore, the effective C170.5 integration limit MUST NOT exceed the C170.2 capability.

The builder’s standalone maximum of 500 files does not override the C170.2 limit.

Current C170.5 resource limits:

Limit	Value
C170.2 supported change set	100 files
C170.5 standalone maximum	500 files
Maximum individual file	5 MiB
Maximum total file content	50 MiB

For a valid integrated delivery, both the C170.2 and C170.5 limits must be satisfied.

Any mismatch or exceeded limit must reject artifact generation.

6. Secret Guard

Before serialization and delivery, the complete payload MUST pass the existing C170.3 Secret Guard.

The scan must include:

* Delivered file contents.
* Verification receipt.
* Impact report data included in the artifact.
* Delivery metadata.
* Other serialized payload fields.

If a suspected credential is detected, generation must stop.

The builder must not bypass or replace the existing Secret Guard.

Important limitation:

Secret scanning is heuristic. A clean result cannot prove that all credentials or sensitive information have been removed.

7. Delivery Artifact Structure

The artifact contains:

Repository

* Base commit SHA.
* Candidate commit SHA.

Change Summary

* Total file count.
* Added file count.
* Modified file count.
* Type-changed file count.
* Total bytes.
* C170.2 risk assessment.

Files

* Complete supported file contents.
* Relative paths.
* Git status.
* Byte counts.
* Individual SHA-256 digests.

Verification

* C170.4 verifier information.
* Verification run ID.
* Candidate commit SHA.
* Completed checks.
* Expected checks.
* Receipt checksum.
* Original verification receipt.
* Attestation metadata.
* Explicit signed: false.

Impact

* C170.2 analyzer identifier.
* Changed files.
* Affected files.
* Affected file count.
* Likely tests.
* Known limitations.

Rollback

* Base commit SHA.
* Candidate commit SHA.
* Rollback guidance.
* automaticRollback: false.

Founder Approval

Default values MUST be:

* required: true
* approved: false
* mergeAuthorized: false
* productionDeploymentAuthorized: false

No generation operation may automatically change these values to an approved state.

8. CLI Usage

Run from the candidate repository checkout:

node scripts/aios-verified-delivery-builder.mjs \
  --base <base-commit-sha> \
  --receipt <c170.4-receipt.json> \
  --impact <c170.2-impact.json> \
  --output <delivery-artifact-outside-repository.json>

All four arguments are mandatory.

The output directory must already exist.

The output path must be outside the source repository.

Existing output files must never be overwritten.

The builder must use exclusive file creation and restrictive file permissions.

9. Read-Only and Security Boundaries

C170.5 is a delivery-generation component.

It does not:

* Modify application source files.
* Modify package metadata.
* Create Git branches.
* Create Git commits.
* Create tags.
* Push to GitHub.
* Create pull requests.
* Approve pull requests.
* Merge branches.
* Deploy to Vercel.
* Modify production data.
* Grant Founder approval.
* Execute provider-generated code.
* Perform automatic rollback.

The output artifact is evidence for subsequent human review.

10. Rollback Policy

The artifact records both the base and candidate commit SHAs.

Rollback must follow a controlled GitHub workflow.

After a reviewed merge:

1. Identify the exact merged commit.
2. Review the production impact.
3. Create a new revert pull request.
4. For merge commits, select the correct mainline parent.
5. Run the required verification workflow.
6. Merge only after explicit Founder authorization.
7. Verify the resulting Production commit SHA.

Direct reset or force-push against main is not an approved rollback procedure.

C170.5 does not execute rollback operations.

14. Final Engineering Principle

C170.5 establishes a verifiable boundary between code generation and code delivery.

The objective is to make AIOS Alpha progressively independent in its ability to:

* Read its own repository.
* Understand proposed changes.
* Validate engineering evidence.
* Generate complete delivery artifacts.
* Preserve security boundaries.
* Require explicit Founder approval.
* Support controlled integration and production verification.

The final objective is not merely to generate code.

It is to establish a reproducible, independently verifiable and human-authorized engineering delivery process.

C170.5 is not merged or deployed until real repository acceptance is complete.
