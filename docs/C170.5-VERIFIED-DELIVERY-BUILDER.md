# C170.5.3 — Verified Delivery Builder

Version: C170.5.3
Status: CI Verified — Awaiting Founder Review and Controlled Integration
Runtime: Node.js 24+
Dependencies: Existing AIOS Alpha dependencies only

## 1. Purpose

C170.5 generates a complete, auditable delivery artifact from an immutable candidate Git commit.

C170.5.3 hardens the Git trust boundary before dependency analysis and artifact generation.

It validates:

- The exact candidate commit checked out as Git HEAD.
- The Base Commit is an ancestor of the Candidate Commit.
- Every changed path resolves to exactly one supported Git Tree entry.
- Only regular Git Tree file modes 100644 and 100755 are accepted.
- Symbolic links, submodules, and unsupported Git object modes are rejected.
- Git Tree validation completes before C170.2 dependency analysis.
- Candidate file contents are retrieved from immutable Git objects.
- The real C170.2 analyzer, C170.3 Secret Guard, and C170.4 receipt verifier are used.
- Founder approval remains mandatory for subsequent integration.

The builder does not authorize merging or production deployment.

## 3. C170.5.3 Security Changes

### 3.1 Base Commit ancestry validation

The Base Commit must be an ancestor of the Candidate Commit.

The builder uses:

`git merge-base --is-ancestor <base-sha> <candidate-sha>`

Expected Git exit behavior:

| Exit status | Meaning | Builder behavior |
|---|---|---|
| 0 | Base is an ancestor | Continue |
| 1 | Base is not an ancestor | Reject |
| Other failure | Git or repository execution error | Reject |

A non-ancestor Base Commit is rejected with:

`AIOS_DELIVERY_BASE_NOT_ANCESTOR`

The builder must not treat an unrelated history, divergent branch, or invalid relationship as a valid delivery range.

This check is performed before parsing the candidate change set.

### 3.2 Git Tree mode validation

Every changed path must resolve to exactly one entry in the Candidate Commit Git Tree.

The builder uses:

`git ls-tree -z <candidate-sha> -- :(literal)<path>`

The literal pathspec prevents wildcard interpretation.

The NUL-delimited output avoids Git pathname quoting ambiguity.

Accepted Git Tree modes:

| Mode | Meaning | Result |
|---|---|---|
| `100644` | Regular non-executable file | Accept |
| `100755` | Regular executable file | Accept |

Rejected Git Tree modes and object types:

| Mode / type | Meaning | Result |
|---|---|---|
| `120000 blob` | Symbolic link | Reject |
| `160000 commit` | Submodule / gitlink | Reject |
| `040000 tree` | Directory tree entry | Reject |
| Any other mode or object type | Unsupported Git object | Reject |

The builder also rejects:

- No matching Git Tree entry.
- More than one matching entry.
- Malformed `ls-tree` output.
- A returned path that does not exactly match the requested path.
- A non-blob object.
- A blob with a mode other than `100644` or `100755`.

Unsupported entries fail with:

`AIOS_DELIVERY_FILE_MODE_UNSUPPORTED`

Malformed, missing, or non-unique entries fail with:

`AIOS_DELIVERY_TREE_ENTRY_INVALID`

The builder must not retrieve a changed file as a blob before validating its Git Tree entry.

### 3.3 Mandatory validation order

The required execution order is:

1. Resolve and validate Base Commit SHA.
2. Resolve and validate Candidate Commit SHA.
3. Require Base Commit and Candidate Commit to differ.
4. Require Candidate Commit to equal the checked-out HEAD.
5. Verify Base Commit is an ancestor of Candidate Commit.
6. Parse the Base-to-Candidate Git diff.
7. Validate every changed path against the Candidate Commit Git Tree.
8. Reject unsupported Git modes and object types.
9. Invoke the real C170.2 dependency impact analyzer.
10. Verify the C170.4 receipt.
11. Retrieve candidate file blobs from the immutable Git object database.
12. Enforce file and total-size limits.
13. Run the C170.3 Secret Guard against the complete payload.
14. Construct the immutable delivery artifact.
15. Return the artifact for a separate controlled write operation.

The following operations must not occur before all changed Git Tree entries pass validation:

- C170.2 dependency impact analysis.
- C170.4 receipt processing.
- Candidate blob retrieval.
- Delivery artifact construction.

Git Tree validation must fail closed.

A failed Git Tree check must prevent downstream analysis and artifact generation.

### 3.4 Candidate HEAD binding

The candidate SHA must:

1. Be a full 40-character commit SHA.
2. Resolve to an existing Git commit.
3. Equal the current checked-out `HEAD`.

If the current checkout does not equal the candidate SHA, the builder fails with:

`AIOS_DELIVERY_CANDIDATE_NOT_HEAD`

This prevents C170.2 from analyzing a different current checkout while C170.5 reads files from another candidate Git object.

### 3.5 Shared 100-file hard limit

C170.2 defines:

`maxChangedFiles: 100`

C170.5.3 independently enforces the same limit before running impact analysis.

| Limit | Value |
|---|---:|
| Maximum changed files | 100 |
| Maximum individual file | 5 MiB |
| Maximum total delivered content | 50 MiB |

The builder rejects a change set as soon as the 101st changed path is detected.

The C170.5 limit must never exceed the current C170.2 analyzer capability.

## 4. Real C170.2 Analyzer Invocation

C170.5.3 imports the existing implementation:

`analyzeDependencyImpact(root, changedPaths)`

The builder does not construct a substitute impact report.

The real analyzer:

- Builds a fresh repository index.
- Reads the actual Git HEAD.
- Checks tracked working-tree cleanliness.
- Reads the tracked-file inventory.
- Builds the TypeScript dependency graph.
- Validates the supplied changed paths.
- Computes direct and reverse dependency impact.
- Produces risk classification and likely test candidates.

C170.5.3 independently validates:

- `schemaVersion === 1`
- `analyzer === "C170.2"`
- `repository.head === candidateCommitSha`
- `changedFiles` exactly equals the Git diff path set
- `changedFileCount` equals the Git diff count
- `readOnly === true`
- `requiresFounderReview === true`
- A valid risk level exists

The generated artifact uses the report returned by the real C170.2 analyzer.

## 5. Optional External Impact Report

The CLI retains an optional `--impact` argument for compatibility and comparison.

If supplied, the external report is compared with the independently recomputed C170.2 result.

Any difference rejects delivery generation.

The external report is never used as the authoritative impact result.

## 6. C170.4 Receipt Verification

The builder invokes the actual interface:

`verifyVerificationReceipt(receipt, expectedCommitSha)`

The receipt must:

- Pass schema validation.
- Match the exact candidate commit SHA.
- Match the fixed full verification profile.
- Contain every expected successful check.
- Pass checksum validation.
- Report a successful overall result.

The receipt checksum is not a cryptographic signature and does not authenticate the runner or receipt author.

A test-only injected command executor must not be described as real CI execution evidence.

## 7. Git Diff and Immutable File Integrity

The builder compares:

`baseCommitSha → candidateCommitSha`

Supported changes:

- `A`: Added.
- `M`: Modified.
- `T`: Type changed.

Unsupported changes fail closed:

- Deleted files.
- Renamed files.
- Copied files.
- Binary files.
- Invalid UTF-8 content.

The current C170.2 API does not model deleted or untracked proposed files. This limitation is preserved rather than bypassed.

All delivered file content is read from the candidate Git object database using:

`git cat-file blob`

This operation is only permitted after the corresponding Git Tree entry has passed mode and object-type validation.

The builder does not use working-tree contents as the delivery source.

Every file record includes:

- Repository-relative path.
- Git change status.
- Byte count.
- SHA-256 digest.
- Complete UTF-8 content.

The serialized artifact also receives a SHA-256 digest.

## 8. Worktree Requirements

The current C170.2 analyzer operates on the checked-out working tree.

Before delivery generation:

- The checked-out `HEAD` must equal the candidate SHA.
- Tracked working-tree files must be clean.
- The candidate changed files must be tracked at the candidate commit.
- The candidate must be committed before analysis.

Untracked files are not used as candidate delivery content.

The analyzer's existing tracked-worktree validation remains authoritative.

Git Tree validation is an independent earlier gate and does not replace the C170.2 worktree checks.

## 9. Secret Guard

Before artifact serialization, the complete payload is passed to:

`assertNoSecretsBeforeProviderDispatch(payload)`

The scan includes:

- Delivered file contents.
- Verification receipt.
- Impact report.
- Delivery metadata.
- Rollback information.
- Founder approval metadata.

A suspected credential blocks generation.

The Secret Guard is heuristic. A clean result does not prove that all secrets have been removed.

## 11. CLI Usage

Run from the candidate repository checkout.

First, generate a C170.4 receipt using the fixed verification plan:

`node scripts/aios-engineering-verification-runtime.mjs verify`

Save its JSON output outside the repository.

Then generate the delivery artifact:

`node scripts/aios-verified-delivery-builder.mjs --base <base-commit-sha> --receipt <c170.4-receipt.json> --output <delivery-artifact-outside-repository.json>`

Optional external impact comparison:

`node scripts/aios-verified-delivery-builder.mjs --base <base-commit-sha> --receipt <c170.4-receipt.json> --impact <expected-c170.2-impact.json> --output <delivery-artifact-outside-repository.json>`

The output directory must already exist.

The output path must be outside the source repository.

Existing output files are never overwritten.

The builder uses exclusive file creation and restrictive file permissions.

## 17. Engineering Principle

C170.5.3 strengthens the boundary between candidate Git history, Git object types, dependency analysis, and code delivery.

The objective is to make AIOS Alpha independently capable of:

- Reading its own repository.
- Identifying candidate changes.
- Verifying commit ancestry.
- Rejecting unsupported Git Tree objects.
- Running its real dependency analyzer.
- Validating verification evidence.
- Generating complete delivery artifacts.
- Preserving security boundaries.
- Requiring explicit Founder approval.
- Supporting controlled integration and production verification.

The objective is not merely to generate code.

It is to establish a reproducible, independently verifiable and human-authorized engineering delivery process.
