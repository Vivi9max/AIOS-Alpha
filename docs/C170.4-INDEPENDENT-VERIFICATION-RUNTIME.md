# C170.4 Independent Verification Runtime

## 1. Objective

C170.4 introduces a repository-owned verification runtime.

The runtime independently executes a fixed verification plan and produces a structured verification receipt.

Provider-generated content cannot choose, append, replace, or skip verification commands.

## 2. Verification plan

The fixed plan contains:

1. C170.1 Repository Intelligence tests
2. C170.2 Dependency Impact tests
3. C170.3 Secret Guard tests
4. C170.3 Provider Security tests
5. C170.3 Provider Adapter tests
6. C169.8-D2.1 control-plane verification
7. Project continuity verification
8. TypeScript typecheck
9. Production build

Commands execute sequentially.

The runtime stops after the first failed step.

## 3. Security boundaries

- No shell execution.
- No provider-supplied commands.
- No arbitrary command arguments.
- No provider-controlled verification plan.
- Child processes receive an environment allowlist.
- Raw stdout and stderr are not copied into the receipt.
- Output is represented by SHA-256 digests.
- Every result is associated with the repository HEAD and branch.
- A failed process, signal, timeout, or non-zero exit code fails verification.
- Exact candidate commit verification requires the checkout HEAD to match the expected commit SHA.
- GitHub Actions workflow runs are matched by exact commit SHA, not by prefix or partial match.
- A checkout HEAD mismatch fails verification with explicit diagnostic evidence.

## 4. Receipt

The receipt contains:

- schemaVersion
- verifier
- runId
- repository commit SHA
- expected commit SHA
- checkout reference evidence
- checkout HEAD consistency status
- repository branch
- verification profile
- status
- start and completion timestamps
- per-step command identity
- per-step exit status
- per-step duration
- stdout and stderr hashes
- executed and expected check counts
- receipt SHA-256 checksum
- Founder review requirement

The receipt does not store raw process output.

## 5. Receipt trust limitations

The receipt checksum detects accidental or unsophisticated modifications.

It is not a digital signature and does not prove the identity of the process that created it.

A locally generated receipt is not a signed GitHub Actions attestation.

A future delivery module must not treat this checksum alone as sufficient proof of trusted CI execution.

## 6. Source mutation boundary

The runtime does not intentionally modify tracked source files.

The production build may generate ignored build artifacts and caches.

No repository commit, push, merge, deployment, or production data mutation is performed by this module.

## 7. Founder approval boundary

A successful verification does not authorize:

- repository writes
- staging commits
- pull request merges
- production deployment
- autonomous approval
- changes to Founder permissions

Explicit Founder approval remains mandatory.

## 8. Local execution

Run the unit tests:

```bash
node --test scripts/aios-engineering-verification-runtime.test.mjs
```

Run the complete verification plan:

```bash
node scripts/aios-engineering-verification-runtime.mjs verify
```

The complete run requires the repository dependencies to be installed.

## 9. Acceptance criteria

- The runtime uses a fixed repository-owned command plan.
- Provider output cannot control command execution.
- Every check is associated with a repository commit SHA.
- Checkout HEAD consistency is enforced against the expected commit SHA.
- GitHub Actions workflow runs are matched by exact commit SHA.
- SHA mismatch diagnostics are explicit and do not weaken SHA validation.
- Verification stops on first failure.
- Receipt structure and checksum are validated.
- Raw command output is not embedded in the receipt.
- Existing C170.1-C170.3 tests remain unchanged.
- Both GitHub Actions workflows run C170.4 unit tests.
- Typecheck and production build remain required.
- Founder review boundaries remain unchanged.
